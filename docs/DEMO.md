# Lifecycle Demo for 0.3.1

The source Demo uses the current managed SDK, its default relationalStore and the same startup/page API used by consumers. The HAR-only consumer is built independently and must resolve the exact final HAR; source Demo compilation is not that evidence.

Run `python3 scripts/generate-sample.py --check` and start `node scripts/serve-demo-fixture.cjs --host 0.0.0.0 --port 8088 --origin http://192.168.1.2:8088/`. Set the generic Demo origin to your reachable test host. The fixture is sample content only; it does not establish real business H5 acceptance.

The Demo creates one manager from EntryAbility. Consent and foreground are facts; UI renders this startup call's progress/return and keeps an independent sample gate. This public Demo displays its own explanatory text and uses an explicit Enter button. It is a generic example, not a required business-App layout. Ordinary package failure permits online entry; a Retry button is only shown for interruption/deferred or invocation errors, not as the gate for an ordinary package failure. Web associates its controller, prepares the original cookie/bridge and loads the unchanged HTTP URL once. The Demo currently uses attached Web controllers for the synchronous resource-cache callback. Hosts can use the no-page API18+ operation described in the integration guide; API12–17 still require an associated controller. Page destruction cancels only its page work.

For a ready activation experiment, use a higher fixture version, let the original process prepare it and confirm ready without switching its in-use package. Stop and restart the isolated process preserving data, then check activation before page binding. Reconstructing a manager in a host test is not real cold-process evidence. Use natural five minutes for scheduler runtime evidence; do not shorten the production interval.

The current default root isolates old Demo Preferences directories and old low-level data. Do not clear or migrate those directories to manufacture a first run. Use a separately authorized isolated installation/root for first-run runtime work. Existing business installations must not be replaced by a sample build.

The Demo displays numeric download progress only while its total is known, uses indeterminate presentation for other work and stops first-install UI from the actual startup result. Its presentation is independent of a host App. API12 runtime testing is skipped. Isolated API26 development candidates have selected storage, ZIP, download and ArkWeb results, without proving every host scenario. API12–17 resource-cache clearing without an associated Web remains open; see [managed integration](MANAGED-INTEGRATION.md) and [validation status](VALIDATION.md).
